# Changelog

All notable changes to this project will be documented in this file.

The format is based on Keep a Changelog, and this project aims to follow Semantic Versioning.

## [Unreleased]

### Fixed
- `overview_df` and `Experiment.metadata` could hold different values for the same cell, and did in real user files. Either half of an edit could go missing: the Data Upload page re-merged the uploaded workbook on **every rerun** — `st.file_uploader` keeps its file for the whole session, and `_render_metadata_uploader` had no submit guard — so an applied edit was reverted in the overview table one rerun later while the experiment's own metadata kept it. The grid and the Dataset Overview then showed one number and the time-series and results pages another, and a reprocessing run with metadata refresh resolved it by pulling the reverted value back over the stored one, destroying the edit on both sides. The success message said it had worked throughout, because it was read from session state rather than from the data. The sheet now owns those columns and the dataset closes the gap from four sides: `add_experiment` aligns the experiment it is given with its overview row (every experiment enters through it — ingestion, reprocessing, a load, a merge — so a pipeline that transformed an overview column gets it put back); `update_overview_df` pushes a merged sheet into the experiments; `save_to_hdf5` **raises** rather than writing a dataset where the two disagree, naming the experiments and columns; and `load_from_hdf5` repairs a file written before the guarantee existed, records what it corrected in `metadata_repair_report`, and the Home page surfaces it — so an affected file heals on open. `ExperimentalDataset.metadata_divergences()` reports and `synchronize_experiment_metadata()` resolves. Two things the sheet deliberately does not own: the `Processed` flag, which is derived and changes without any metadata changing, and keys a `metadata_retrival_function` adds that are not overview columns. Values are compared by value, not by type, so a round trip through HDF5 or Excel is not a divergence. See [guide/dataset.rst](https://github.com/jschneidewind/pyKES/blob/main/docs/guide/dataset.rst).
- The metadata sheet is merged **once per uploaded file**, tracked by the uploader's `file_id`, rather than on every rerun. Besides reverting edits, the old behaviour re-parsed the workbook on every interaction, which in stlite's single-threaded runtime is a per-click cost. Clearing the widget lets the same workbook be uploaded again.
- Applying a metadata edit moved the page, and sent the grid back to its first columns. Two causes, both measured in headless Chromium with the button already in view. The grid's widget key carried a revision counter bumped on every apply — horizontal scroll survives a rerun of either scope (1200 -> 1200 px) and is lost only when the key changes (1200 -> 0), so the key is now bumped by an uploaded workbook and nothing else. And the `st.success` box appeared and disappeared, which changes the height of the section and shifts everything below it, so the status is now always the same two captions. **The scope of the rerun was not one of the causes**, though an earlier measurement said it was: the browser automation had scrolled the off-screen button into view before clicking it and measured its own scrolling. That mistake is why the status-height contribution went unnoticed at first, and why the editor briefly avoided an app-scoped rerun it now needs.
- Metadata edits went missing, and dragging a value down several rows filled some of them at best. Saving each cell as it was committed meant a rerun **in the middle of the gesture**, which re-rendered the grid and dropped what had not been sent yet. The grid is back in an `st.form`, where a committed cell sends nothing until the button is pressed: a drag-fill arrives as one delta covering every cell it touched, and all of them are stored. There is no way to have both — either every cell is reported as it happens, or the gesture is left alone and reported on submit.
- A fraction typed into a whole-number metadata column was silently rounded. An Excel column of whole numbers arrives as `int64` and `st.data_editor` takes its field type from the dtype, so an irradiation start corrected to 62.5 was stored as 62 — and neither an explicit fractional `step` nor a decimal format changes that, only the dtype does. `metadata_editor_view` widens its editable integer columns and `assign_overview_value` widens the overview column to match. This bit exactly the columns an app declares as processing-relevant: irradiation windows, irradiance, volumes.
- `st.column_config.NumberColumn` formats printf-style and has no `g` conversion, so the results table's default spec `'.4g'` rendered `1.2345e-5` as `0.00001234` and `12960000` as `1296000`, and an uppercase `'.4G'` was rejected outright with the cells marked invalid. Every instruction that does not set its own `format` was affected. Formatting moved to a `pandas.Styler`, which honours Python format specs in full while leaving the frame numeric so the header sort still compares magnitudes.
- `pyKES.utilities.max_rate` reported a rate driven by a slow instrument oscillation on wells where the variogram could not see that oscillation at all. The variogram probes lags only up to `VARIOGRAM_MAX_LAG_FRACTION` (5 %) of the run, so a stirring or temperature-control wander with a period of several minutes is still *rising* at the longest lag it measures — indistinguishable there from the reaction's own curvature, which the variogram models explicitly with a `curvature · h⁴` term. The wander was therefore booked as chemistry, the nuisance component came back with a correlation time of 10–32 s (too short to hold a 270–320 s oscillation), and the kinetic Matérn-5/2 was left as the only component able to explain the wiggles: its length scale collapsed onto them, the rate curve oscillated about zero instead of decaying, and the reported maximum came off a crest. This is the same failure mode as the 0.1.8 nuisance-floor fix, reached by a different route — there the correlated component was discarded outright, here it was measured too short. Note the kinetic floor `KINETIC_SEPARATION_FACTOR · nuisance_lengthscale` was no protection: at 20–63 s it never exceeded `LENGTHSCALE_MIN_STEPS · dt` (68 s on a 3.4 s grid), so the separation constraint was inert.
- On a 176-well calibration plate (160 reaction wells, 16 blanks) three blanks were affected. `AE-854_B2` reported 4.00e-6 µmol/s — inside the range of the 160 real experiments and **above the weakest of them** (2.58e-6) — on a rate curve oscillating between ±4e-6 with 35 turning points. The three now return 9.4e-7, −3.9e-8 and 3.4e-7, with 8, 3 and 21 turning points; the other 13 blanks were never affected and are unchanged. All three were already flagged `max_rate_not_significant` before the fix, so only the reported number was wrong, not the verdict.
- The Analysis Results Table sorted its columns lexicographically: clicking the header of an apparent-quantum-yield column put `9` above `18`, and `100` between `10` and `2`. `build_cell_text` formatted every value into a string before it reached the DataFrame, so the Arrow column handed to `st.dataframe` was text and the frontend had nothing but text to compare. The table now holds the resolved **numbers**, and `format` and `unit` are applied on the display side of a `pandas.Styler` — the same digits and the same unit suffix, sorted by magnitude. Verified in headless Chromium: sorting a styled column ascending orders `1.234e-05`, `9`, `18`, on the underlying values rather than the displayed text. `format` is therefore a **Python** format spec, honoured in full; a result that genuinely resolves to a string is passed through unformatted. No third-party grid is introduced — an AgGrid dependency would also break the stlite bundle. **Breaking (display only)**: an instruction defining `error` no longer renders `value ± error` in one cell but gives the uncertainty a sortable column of its own, `label (±)`; an unresolvable cell renders as Streamlit's `None`, as a missing value does in every other table in the app; and the CSV export holds numbers rather than pre-formatted text, which is what a spreadsheet should have been getting all along. See [plotting_instructions.md](https://github.com/jschneidewind/pyKES/blob/main/docs/plotting_instructions.md).
- A colour a user typed into the overview sheet could take a whole page down. `Experiment.color` went straight into `go.Scatter(marker=dict(color=...))`, so a misspelt `ligthblue` raised `ValueError: Invalid value of type 'builtins.str' received for the 'color' property` and Streamlit showed a traceback where the figure should be — one bad cell in a 44-experiment sheet cost the entire plot. The new [plot_colors.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/plotting/plot_colors.py) resolves the colour where it is read for plotting: `matplotlib.colors.is_color_like` (public, exception-free, and matplotlib is already a hard dependency) decides whether it can be drawn, `to_hex` converts it — which also neutralises the matplotlib-only names `'tab:blue'` and `'C0'` that pass the check and are then rejected by plotly — and anything unusable becomes `FALLBACK_PLOT_COLOR`, blue. CSS functional notation (`'rgb(...)'`, `'hsl(...)'`) is passed through, since plotly accepts it and matplotlib does not. The stored value is left alone in `overview_df`, `Experiment.color` and the metadata listings, so the mistake stays findable, and each page renders one warning naming the experiments and the values they declare — the fail-fast rule cannot be honoured literally where blue *is* the requested behaviour, but it need not be silent. Applied in `build_trace_specifications` (time series), `create_plotly_figure` (analysis results) and `Fitting_Model.visualize_optimization_results` (matplotlib).
- The same guard catches a second failure mode that was never an exception and therefore never noticed: an **empty** colour cell. `metadata_dict.get('color', 'black')` finds the key present and returns the float `nan` pandas put there, so `Experiment.color` becomes `nan` and the documented `'black'` default never applies. plotly accepts `nan` without complaint and falls back to its own default, so the experiment was quietly drawn in a colour nobody asked for. `is_color_like(nan)` is `False`, so it now lands on blue with the rest and is named in the warning.
- Reprocessing never set the `Processed` flag back to `'True'`. Harmless until now only because nothing ever cleared the flag for an experiment that had been ingested — the metadata editor does, so `reprocess_experiment_by_name` has to be able to clear it again, and it now marks the row on success. A failing run still leaves the flag alone, along with the previous `processed_data`. `reprocess_single_experiment` stays flag-free: it takes an `Experiment`, not a dataset, and has no overview sheet to write to.
- `update_overview_df` silently turned the flag into `NaN` for every row a re-uploaded sheet changed. The differing-row branch took the incoming row wholesale, and an Excel sheet carries no `Processed` column, so the flag vanished and came back as `NaN` on the concat — which `select_unprocessed_experiments` read as "unprocessed" by accident rather than by decision. The merge of one overlapping row now lives in `merge_overview_row`, which sets the flag explicitly, and the method takes an optional `processing_relevant_columns` so the decision can be made properly: without it every difference invalidates (today's effective behaviour, made explicit), and with it only a difference in a declared column does — so re-uploading a sheet with a corrected comment no longer costs a processing run. The Data Upload page passes the dataset's own declarations, or `None` for a dataset that declares nothing.

### Added
- `ExperimentalDataset.experiment_column`, persisted as an HDF5 root attribute and defaulting to `'Experiment'` for files that predate it. Knowing which row belongs to which experiment is what makes the metadata invariant enforceable, and the dataset had no way to know. `update_overview_df` adopts the key column it is given, and `merge_hdf5_files` adopts the source files'. Schema **1.2**, together with the metadata guarantee itself; both are additive, so a 1.1 reader ignores the attribute and a 1.2 file loads in a 1.1 reader unchanged.
- `ExperimentalDataset.metadata_divergences`, `synchronize_experiment_metadata` and `metadata_repair_report`, plus the module-level `values_agree`, `overview_metadata_for_experiment`, `experiment_metadata_divergences`, `apply_overview_metadata` and `describe_metadata_divergences` in [database_experiments.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/database/database_experiments.py). `add_experiment` now returns what it had to correct, which is what lets a load report it. New test module [test_metadata_consistency.py](https://github.com/jschneidewind/pyKES/blob/main/src/tests/test_metadata_consistency.py) covers the comparison, what the sheet owns, alignment on entry, propagation from a merge, the save refusal and the load repair.
- **A fully configured example app and a real dataset to drive it with.** `examples/external_repo` was a stub whose processing function returned `{}` and which imported its wiring from the test suite; it is now a self-contained app with `parameters.py` (declarations, analysis settings, plotting instructions for all three pages), `metadata_functions.py`, `raw_data_functions.py` and `processing_functions.py`, and two upload handlers for the two instrument modes an app of this kind owns. The processing is real: each trace is cut to its irradiation window, averaged into 10 s bins, converted to an amount of substance, and handed to `pyKES.utilities.max_rate`, whose fit returns the largest sustained rate with an uncertainty; that rate becomes an apparent quantum yield through `pyKES.utilities.calculate_efficiency`. So the example exercises `max_rate`, the unit handler, `offset_correction`, `time_series_resampling`, every analysis page, the metadata editor, reprocessing, merging and the HDF5 round trip.
- `examples/example_data`: one metadata workbook, the twelve raw sensor files it names, and `example_dataset.h5` — the same six-experiment photocatalytic water-splitting series already processed, so the analysis pages can be reached without ingesting anything. `build_example_dataset.py` regenerates the file from the app's own pipeline. H2 comes out at roughly twice O2, which is the stoichiometry of water splitting and a sign the wiring is right; the expected numbers are tabulated in [examples/README.md](https://github.com/jschneidewind/pyKES/blob/main/examples/README.md), which is a step-by-step walkthrough of every feature with what to look for at each step, including the paths that used to be broken.
- A parsimony tie-break on the kinetic length scale in `fit_hyperparameters`, with the constants `KINETIC_PARSIMONY_MARGIN` (0.01) and `KINETIC_SMOOTH_FRACTION` (0.5). The marginal likelihood is now asked twice — once freely, once with the kinetic length scale confined to the smooth end of its range by the new `fit_smooth_alternative` — and the smooth fit is kept unless the free one is better by more than `KINETIC_PARSIMONY_MARGIN` nats per fitted point. The point is how *narrowly* the likelihood preferred the collapsed fit: on `AE-867_B2` and `AE-868_C2` the wigglier curve was ahead by only **0.0059 and 0.0065 nats per point** (about 6 nats over ~1030 points), against a margin of 0.01. A wigglier curve always fits marginally better, so an indifferent likelihood was enough to win; now flexibility has to be earned. `AE-854_B2` flips one stage later and shows the rule cooperating with artifact rejection rather than fighting it: its unmasked first ~800 s genuinely are spiky, so the first fit keeps the flexible answer (0.089 nats per point, well clear of the margin), and only the post-artifact refit — once those samples are downweighted — finds the wiggles no longer worth their margin (117.6 s -> 738.0 s). Both fits have the same three free parameters, so this is a tie-break rather than a likelihood-ratio test, and it can only act where the likelihood is flat. It must be a *restricted refit* and not an extra starting point — started long but left free, Nelder-Mead walks straight back down to the wiggly optimum. Cost is one extra Nelder-Mead run on the decimated subset.
- Three blank wells committed as real-data fixtures in `src/tests/data/max_rate_real/` (`AE-854_B2`, `AE-867_B2`, `AE-868_C2`), and three parametrized tests over them in [test_max_rate_real_data.py](src/tests/test_max_rate_real_data.py): the maximum stays under a ceiling taken from the plate's own smallest genuine rate, the kinetic length scale is no longer a small multiple of its floor (the guard on the mechanism, since a blank can come out near zero for the wrong reason when two crests cancel inside the averaging window), and the result is far below the collapsed value (so a silent regression cannot pass on a loose ceiling). They are deliberately kept out of `REAL_TRACES`: `AE-854_B2` masks 18 % of its samples because its first ~800 s genuinely are spiky, so the "residual equals the fitted noise" and "under 5 % masked" properties every reaction trace satisfies are the wrong questions for it. Until now `max_rate_not_significant` was only ever exercised on a synthetic control, and the six validation blanks the 0.2.0 entry cites were never committed.
- **Metadata can be corrected in the app.** Section **4. ✏️ Edit Metadata** of the Data Upload page renders `overview_df` as an `st.data_editor` grid, one row per experiment. Streamlit's editor already supports multi-cell selection, drag-fill and pasting a block straight out of Excel, so correcting one column across forty experiments is a paste rather than forty edits — and no bulk-edit UI of our own was needed. Nothing is stored until **Apply metadata changes** is pressed, and the grid sits in a `st.form` **inside an `st.fragment`** — both halves load-bearing. The form is what makes the gestures work: inside one a committed cell sends nothing and triggers no rerun, so a drag-fill or a pasted block is left undisturbed and arrives as a single delta covering every cell it touched (measured on the real page: one value dragged down three rows stored and flagged four experiments together). Applying then ends in `st.rerun(scope="app")`, because what an edit changes is shown by section 3 — its standing warning and its "Only experiments needing reprocessing (n)" checkbox — which the page body draws above the editor: the warning now appears and the checkbox becomes selectable on the same press instead of staying stale until the next page interaction. That costs a page run, which is what every page-level interaction already costs, and it does not cost the scroll position: measured with the button in view, 686 -> 686 px in an isolated layout and 1492 -> 1499 px on the real page, the 7 px being the new warning pushing what follows down by its own height. What keeps it still is that the grid's widget key does not change on submit, and that the status area is always the same two captions rather than an `st.success` box that comes and goes — changing the section's height shifts everything below it and reads as the page moving. The section sits behind the `any_active_job` guard, so a grid over `overview_df` never renders while a job is flipping the flags it displays; "📦 Merge HDF5 Files" and "💾 Download Dataset" are renumbered 5 and 6. The widget key carries a revision counter bumped only by a merged workbook, where re-seeding the grid is the point — `st.data_editor` keeps its `edited_rows` delta in session state and replays it over whatever data it is handed, so after an upload a stale delta would reassert the values the sheet just replaced.
- The policy behind that grid is declared by the **dataset**, not by the app's configuration, in two lists in `processing_parameters`: `metadata_used_for_raw_data_loading` (shown but locked — a filename or a well number selects *which* measurement an experiment is, so correcting one means uploading the corrected sheet and the raw files again; the derived `Processed` flag is not a column of the grid at all) and `metadata_used_for_processing` (editable, and clears the experiment's `Processed` flag). Everything else is editable and costs nothing; `color` and `group` are re-derived onto the `Experiment` at once, exactly as `reprocess_single_experiment` does, so a corrected colour takes effect without a reprocessing run. Requiring **both** keys is the backward-compatibility gate and the safety rule in one: `processing_parameters` reaches a dataset from the file it was loaded from, so a file written before an app declared them carries neither and gets an explanatory note instead of a grid, and a dataset that declares nothing locked can never expose a raw-data-loading column as editable by omission. A declared column the sheet does not have is reported rather than ignored. New module [metadata_editing.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/database/metadata_editing.py), Streamlit-free and testable on its own; the grid is [metadata_editor.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/streamlit_app/components/metadata_editor.py). Full policy, the flag table and the old-file path: [metadata_editing.md](https://github.com/jschneidewind/pyKES/blob/main/docs/metadata_editing.md).
- Section 3 of the Data Upload page gained the other half of that loop: a standing warning naming every experiment whose stored results no longer follow from its metadata — rendered above the active-job guard, so it stays visible while a job runs — and a checkbox, **"Only experiments needing reprocessing (n)"**, which overrides the experiment multiselect with exactly that list and is disabled when the list is empty. `select_experiments_needing_reprocessing` is what backs both: experiments the dataset actually **holds** whose row is not flagged `'True'`. Being held is what separates them from what `select_unprocessed_experiments` returns — a row that was never ingested needs *processing*, and has no stored raw data to reprocess — so no extra session state is needed to remember the warning across reruns.
- `PROCESSED_FLAG_COLUMN`, `PROCESSED_TRUE` and `PROCESSED_FALSE` in [database_experiments.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/database/database_experiments.py), and `mark_experiment_processed` / `mark_experiments_unprocessed` in [data_processing.py](https://github.com/jschneidewind/pyKES/blob/main/src/pyKES/database/data_processing.py). The flag was compared and written as bare string literals in two modules, and is now touched in five places. It stays text rather than becoming a bool because it round-trips through Excel and HDF5; a bool column is also what raised `TypeError: Invalid value 'True' for dtype 'bool'` in 0.2.0. Note that `read_in_experiments_multiprocessing` still neither reads nor writes the flag — it processes every file its keywords match, which already contradicts `docs/guide/dataset.rst` and is left alone here. The Streamlit page does not use that entry point.
- Two column selectors above the Analysis Results Table: **Results to show** (which instructions become columns, all of them by default) and **Metadata to show** (columns of `overview_df`, joined to the left of the results, none by default so the table looks as it did). The metadata columns are taken from the overview sheet unchanged, so each keeps its own dtype and sorts correctly with no extra handling; the join is on the sheet's `Experiment` column, and a dataset whose sheet has no such column offers none and says so.

### Changed
- **Breaking (display only)**: the results table shows the number alone in each cell, and names the unit in the column header instead — `'H2 max. rate'` with `'umol / h'` becomes the header `H2 max. rate (umol / h)`, and its uncertainty `H2 max. rate ± (umol / h)`. Repeating a unit in every row costs width, makes the numbers harder to compare down the column, and puts text in a cell whose value is a number. `unit` keeps its other, load-bearing job of deciding what a `Quantity` is converted into. The error column's suffix is now a bare `±` rather than `(±)`, so it does not collide with the parenthesised unit after it.
- **Reference value updated**: `EA-696-Logger-4` in `REAL_TRACES` moves from 4.66284e-05 to 4.404686e-05 (−5.5 %), the one existing pin the parsimony margin shifts. It is a low-signal UniAmp hydrogen trace whose wigglier fit gains only 0.0037 nats per point, so the smooth fit is taken; it is not the trace nearest the margin, it is the one whose reported maximum is most sensitive to being smoothed, because at 4.4e-5 µmol/L/s its maximum sits close enough to its own noise for the extra stiffness to shave a few percent off it. The other ten pins move by ≤2.4 % (seven of them by ≤0.3 %) and stay inside the existing 5 % tolerance, and all 31 synthetic tests are unchanged. The value was re-pinned rather than the tolerance loosened.
- A new module-level helper `fit_from_starting_lengthscale` carries the Nelder-Mead call that the multi-start loop and the smooth refit share.
- The example app in `examples/external_repo` now exercises both new features end to end. `PROCESSING_PARAMETERS` declares the two metadata lists, `PLOTTING_INSTRUCTIONS` gains a `results_table_instructions` block with one `error` path — the Results Table page previously errored out with "No 'results_table_instructions' found" — and the example `processing_function`, which returned `{}`, now derives two deliberately crude observables (a peak-to-trough difference over the irradiation window, with the pre-irradiation scatter as its uncertainty). Both depend on declared processing columns, so editing a cell and reprocessing is visible on the Results Table page rather than having to be taken on trust.
- `CLAUDE.md` is corrected on two stale points this work touched: `src/pyKES/streamlit_app/pages/` does not exist (external repos supply their own page files), and the app is run as `streamlit run examples/external_repo/Home.py` — there is no entry script inside the package.

## [0.3.0]

### Added
- The HDF5 key-escaping convention is now public API: `sanitize_key`, `restore_key` and the `KEY_SLASH_PLACEHOLDER` constant in [database_experiments.py](src/pyKES/database/database_experiments.py). Metadata keys routinely contain slashes — `Irradiance A [mW/cm2]`, `Catalyst loading [wt% Rh/Cr]` — while `/` is also the separator of a nested HDF5 path; escaping the one inside the other is what keeps a joined path splittable. This was previously the private `_sanitize_hdf5_key`, with no inverse. It is exposed because it is the contract between the on-disk layout and anything that builds a path-addressed index over it, and a convention consumed from outside this package needs to be nameable and tested rather than incidental.
- `save_to_hdf5` accepts `compression` (a filter passed to h5py, e.g. `'gzip'`) and `verbose`. Compression is applied by the new `compression_arguments` only to arrays of at least `COMPRESSION_MINIMUM_ELEMENTS` (128) elements, since HDF5 refuses to compress scalar datasets outright and the filter costs more than it saves on very small arrays. It is transparent to readers, so a compressed file loads unchanged and needs no `SCHEMA_VERSION` bump. `verbose=False` suppresses the per-experiment print when writing one file per experiment in a loop.
- [src/tests/test_key_escaping.py](src/tests/test_key_escaping.py), 29 tests covering the escaping round trip, the join-and-split property the escaping exists for, non-string keys, and the compression thresholds. The round trip is asserted rather than assumed because a silent change to the placeholder would corrupt an index built against files written by a different pyKES version, and would otherwise fail nowhere.
- A test workflow, [.github/workflows/tests.yml](.github/workflows/tests.yml), running `pytest` on every pull request and on pushes to main. There was no test workflow at all, which made "main is releasable" an assumption rather than a fact. It installs with `uv sync --locked`, so a lockfile that no longer matches `pyproject.toml` fails there rather than at release time.

- Sphinx documentation, ready to deploy on Read the Docs: `.readthedocs.yaml` at the repository root, `docs/conf.py`, and a `docs` extra in `pyproject.toml` (`sphinx`, `sphinx-rtd-theme`, `sphinx-copybutton`, `sphinx-design`, `sphinxcontrib-mermaid`, `myst-parser`, `linkify-it-py`), plus a `dev` extra pulling in `docs` and `pytest`. The documentation root is `docs/` itself rather than a new `docs/source/`, so the existing deep-dive documents keep the paths that this changelog and the module docstrings already link to, and keep rendering on GitHub. Build locally with `sphinx-build -b html docs docs/_build/html`.
- Guide pages under `docs/guide/`, covering the parts of the package that had no prose documentation: [architecture.rst](docs/guide/architecture.rst) (how the modelling half and the data half meet in the fitting module, with a module dependency map), [reaction_networks.rst](docs/guide/reaction_networks.rst) (mechanism syntax, the mass-action rate law, multipliers, stiffness), [light_absorption.rst](docs/guide/light_absorption.rst) (why an excitation rate cannot be a constant when the chromophore ratio shifts, and which of the four variants to use where), [fitting.rst](docs/guide/fitting.rst) (path-resolved conditions, choosing a loss function, weighting, bounds, diagnosing a bad fit), [pathways.rst](docs/guide/pathways.rst) (photon budgets, cycles, reconvergence, and why the bars are logarithmic), [dataset.rst](docs/guide/dataset.rst) (the three-callable ingestion contract, what HDF5 will store, reprocessing), [units.rst](docs/guide/units.rst) and [streamlit_app.rst](docs/guide/streamlit_app.rst). Twelve mermaid flowcharts illustrate the code paths; all twelve were validated against mermaid 11.12.1 rather than only eyeballed, since a diagram with a syntax error fails silently in the browser.
- API reference under `docs/api/`, eight autodoc pages grouped by subpackage, driven by `sphinx.ext.napoleon` from the NumPy-style docstrings and cross-linked to the guide pages that explain each module.
- Example figures in `docs/_static/images/`, generated by the new [docs/generate_example_figures.py](docs/generate_example_figures.py) from the package itself, so a change in behaviour shows up in the documentation the next time it is run. The fitting example manufactures three synthetic experiments from an analytic consecutive-reaction solution and recovers both rate constants to better than 0.5 %, which makes it a check as well as an illustration. The figures are committed, so a documentation build needs neither a display nor a simulation.
- A proper [README](https://github.com/jschneidewind/pyKES/blob/main/README.md): badges, install, and the four things the package does — simulate, fit, extract maximum rates, trace the photon budget — each with a runnable snippet and the figure it produces, followed by a table of what else is in the box and a documentation index.

## [0.2.1]

### Fixed
- The ingestion progress bar on the Data Upload page never appeared in the browser deployment: pressing "🚀 Process data" showed nothing at all until processing had finished. stlite runs Streamlit inside Pyodide on the browser's single event loop, with no separate script-runner thread, so everything `read_in_experiments_single_threaded` wrote through its `progress_callback` was queued and only delivered once the loop it was reporting on had ended — at which point the page cleared the placeholder and drew the result messages instead. Under `streamlit run` the same code worked, because there the script has a thread of its own while the server's event loop keeps delivering. The reprocessing section had the same defect.
- Ingestion and reprocessing are now spread across Streamlit runs, one experiment each, by the new module `pyKES.streamlit_app.chunked_processing`. A run has to end for what it drew to reach the browser, so the job is stepped by two `st.fragment`s with a `run_every` timer: `render_job_progress` draws the bar and nothing else, `advance_job` processes one experiment and draws nothing. `any_active_job` lets a page skip sections too expensive to re-render per experiment (the Data Upload page skips the HDF5 merge, the download button, the overview table and the statistics until the job is done), and uploaded files are staged in a `mkdtemp` directory that outlives the run which created them, removed when the job finishes. See [docs/browser_deployment.md](docs/browser_deployment.md).
- Both halves of that design are forced by how Streamlit delivers messages, and both were established by measuring the deployed page in headless Chrome. Stepping the job with `st.rerun()` shows **nothing at all** in the browser: `AppSession` clears unflushed messages on every `SCRIPT_STARTED`, and a run that ends in `st.rerun` is followed immediately by the next one, so the bar is discarded before it is sent. (On a server it survives, because the flush runs on another thread — which is why this looked fixed under `streamlit run`.) Drawing the bar inside the working fragment fails too, less obviously: `ForwardMsgQueue.clear` preserves the deltas of fragments *other* than those rerunning, so a fragment wipes its own output on its own next tick — the browser showed `Processing experiment 1/8` for a whole eight-experiment run and never advanced.
- Expect a bar that appears immediately and climbs, but not once per experiment: the single browser worker thread is busy processing, so only some paints reach the page (three or four distinct states over eight experiments in a probe). Changing the timer interval does not change that.
- A dataset created in a browser (stlite) deployment recorded `'version': None` as the external app's provenance. `get_project_version` reads the app's `pyproject.toml` from disk, but a stlite bundle holds only the files its build script writes into Pyodide's filesystem — `.py` modules and nothing else — so the upward search reached the filesystem root and found none. There is no repository in the browser either, which is why the commit-based stamp it replaces failed there in the same way. The build script has to bundle `pyproject.toml` beside the app package (pyKES-Well-App's `deploy/build.py` now does), and [docs/browser_deployment.md](docs/browser_deployment.md) gained a section on what the bundle must carry besides the modules, with a check that reads the version back out of the built layout.

### Changed
- `pyKES.database.data_processing` exposes the per-experiment steps of both loops as module-level functions: `ensure_processed_column`, `select_unprocessed_experiments`, `ingest_experiment`, `select_experiments_to_reprocess`, `reprocess_experiment_by_name` and `finalize_processing_run`. The seeding of the `Processed` flag as the string `'False'` — the 0.2.0 fix for `TypeError: Invalid value 'True' for dtype 'bool'` — now lives in `ensure_processed_column`, which both `select_unprocessed_experiments` and `ingest_experiment` call, so stepping through experiments one rerun at a time reaches the flag with the same guarantee the loop function had. `read_in_experiments_single_threaded`, `read_in_experiments_multiprocessing` and `reprocess_experiments` are now thin loops over them and keep their signatures, return values and `progress_callback` protocol unchanged, so callers outside Streamlit are unaffected.
- The three submit buttons on the Data Upload page pass `width="stretch"` instead of the deprecated `use_container_width`.
- Removed `_update_ingestion_progress` from the data-upload component; the progress bar is drawn by `chunked_processing.paint_job_progress` and needs no `st.empty` placeholder.
- **Breaking**: the external app's provenance is now its own released version rather than its git commit. `pyKES.utilities.version_information.get_git_commit` is replaced by `get_project_version`, which searches upwards from a given path for the nearest `pyproject.toml` and returns the version declared in it — every external repo embedding pyKES is a Python project with one, and the version number is the identifier its users, issues and changelog refer to, whereas a commit hash only means something to whoever has the repository at hand. The recommended entry becomes `{'app': 'photocat', 'version': get_project_version(__file__)}`; `external_version` stays free-form, so existing dictionaries (including `'commit'` entries in already-written HDF5 files) keep working untouched. `read_version_from_pyproject` now takes the file to read, and the module-level `PYPROJECT_PATH` is renamed `PYKES_PYPROJECT_PATH`. Since the stamp is now a release number, bump the app's version when its processing behaviour changes. See [docs/versioning_and_reprocessing.md](docs/versioning_and_reprocessing.md).

## [0.2.0]

### Added
- Real-data tests for `max_rate`: `src/tests/test_max_rate_real_data.py` runs the pipeline over eleven measured traces committed as plain two-column CSVs in `src/tests/data/max_rate_real/` — five PyroScience oxygen logs, two UniAmp hydrogen logger exports, two short hand-logged runs and the two well-plate wells either side of the nuisance resolution floor (`AE-855_B2`, `AE-855_C2`). They check what synthetic ground truth cannot: that kinetic plus nuisance reproduce each measured trace to within its fitted noise, that the smoothing-free cross-check never disagrees enough to be flagged, and that each of the three branches of the noise characterization is reached by the real data that belongs in it. Reference maximum rates are pinned at 5 % so a change in behaviour on real files has to be looked at rather than absorbed. See the README beside the fixtures for their provenance.

### Fixed
- `pyKES.utilities.max_rate` could report a rate driven by correlated sensor noise when that noise decorrelated close to three sampling intervals. The resolution guard added in 0.1.7 discarded a correlated component whose measured correlation time fell below that floor and re-labelled its whole amplitude as white noise, which left the kinetic Matérn-5/2 as the only component able to explain wiggles that are in fact correlated — so its length scale collapsed onto them and a noise crest became the reported maximum. The guard was all-or-nothing, so a fit landing a fraction of a percent below the floor was treated completely differently from one landing just above it. On a 110-well plate, one well (AE-855_B2) missed the floor by 0.4 % with correlated noise 65 times the white variance and came out 17 % high (0.0438 instead of 0.0364 µmol/h) on a rate curve that oscillated between −0.03 and +0.07 µmol/h instead of decaying — and raised no flag, because the fold also set the nuisance correlation time to the one value that suppresses `strong_correlated_noise`.
- The floor is now a constraint rather than a verdict: a correlation time below `NUISANCE_MIN_LENGTHSCALE_STEPS` sampling intervals is pinned there and the white and correlated variances are refitted under that constraint, so the component is kept instead of deleted. The refit matters — a process held to a longer correlation time explains less of the short-lag variogram and has to return the difference to the white noise, which is what keeps the clamp from understating `white_std` (by a factor of 2.9 on a simulated nuisance at 1.2 sampling intervals). Folding to white now happens only for the two cases that genuinely leave nothing to measure: a component carrying less than `CORRELATED_NOISE_SIGNIFICANCE` of the white variance, and a variogram with fewer lags than the new `VARIOGRAM_MIN_RESOLVED_LAGS` (6), the four-parameter model having no headroom below that. The latter is the real cause of the short-series collapse fixed in 0.1.7, which the old lengthscale test only caught as a symptom; that regression stays covered. New module-level helper `variogram_residuals_at_fixed_lengthscale` performs the constrained refit.
- Rerunning all 110 wells of the plate, AE-855_B2 is the only result that moves; the other 109 are bit-identical, since neither new branch is reached when the variogram resolves a correlation time above the floor.
- `read_in_experiments_single_threaded` raised `TypeError: Invalid value 'True' for dtype 'bool'` as soon as the first experiment succeeded, whenever `overview_df` arrived without a `Processed` column — the ordinary first-ingestion case. The column holds the strings `'True'` / `'False'` everywhere else (it round-trips through Excel and HDF5, and is read back with `dtype=str`), but it was seeded with a bool `False`, giving it bool dtype; current pandas refuses to write a string into that instead of silently upcasting to object as it used to. The same mismatch also made the skip-already-processed mask ineffective, since `.ne('True')` against a bool column is true for every row, so a second ingestion pass would have reprocessed everything.
- Running `pytest` from the repository root hung before a single test started. Collection reached `Untracked/`, whose `plotting_links_test.py` matches pytest's `*_test.py` pattern and draws a figure at import; `plt.show()` then blocked on the window forever. New `[tool.pytest.ini_options]` in `pyproject.toml` points `testpaths` at `src/tests` and adds `Untracked` to `norecursedirs`, so both `pytest` and `pytest .` collect in under a second.

## [0.1.7]

### Added
- Dataset version information: `ExperimentalDataset.version` is a new top-level dictionary (alongside `plotting_instruction`, `group_mapping` and `processing_parameters`) recording the pyKES version, the schema version, the creation, last-modification and last-processing timestamps, and a free-form `external_version` entry for the embedding app. It is written into the HDF5 root as a JSON attribute and shown on the Home and Data Upload pages. Each `Experiment` carries the same kind of dictionary in `Experiment.version`, stamped whenever that experiment is processed, so partial reprocessing runs stay traceable. New module `pyKES.utilities.version_information` provides the helpers, including `get_git_commit` for external apps that want to record the commit of their own processing code; `ExperimentalDataset.set_external_version` and the new `DataUploadConfig.external_version` field feed it in. See [docs/versioning_and_reprocessing.md](docs/versioning_and_reprocessing.md).
- Reprocessing of existing HDF5 files: `pyKES.database.data_processing.reprocess_experiments` (and `reprocess_single_experiment`) rerun the processing step against the metadata and raw data already stored in a dataset, rebuilding `processed_data` without the original raw-data files — the path for applying an improved algorithm to finished files. The metadata is either reused as stored or refreshed from `overview_df` via the optional `metadata_retrival_function`, which also updates `color` and `group`. Experiments whose processing raises keep their previous results. Exposed on the Streamlit Data Upload page as "3. ♻️ Reprocess Existing Experiments", with pipeline and experiment selection, a metadata-refresh toggle and a progress bar.
- Units on the Time-Series page: `time_series_instructions` entries accept optional `'unit_x'` / `'unit_y'` keys, each either a path into the experiment holding the unit string or a literal unit. Units become the axis titles and appear in the hover box. Curves whose y unit differs are drawn against their own y axis, added on the right-hand side, so amounts (`umol`) and rates (`umol / s`) can be shown in one figure. Instructions without units keep the previous single-axis behavior with generic axis titles. See [docs/plotting_instructions.md](docs/plotting_instructions.md).
- Progress reporting for raw-data ingestion: `read_in_experiments_single_threaded` accepts an optional `progress_callback`, called as `(completed, total, experiment_name)` once before the loop (with `total` and `None`) and after each experiment. The Streamlit data-upload page uses it to render a live progress bar naming the experiment being processed.

### Changed
- `streamlit` is now required at `>=1.49`. The components pass `width="stretch"` to `st.dataframe` / `st.plotly_chart`, which older versions reject with `proto.width = width` raising a type error when a page renders a table or a figure.
- **Breaking (display only)**: the analysis results table is transposed — experiments are now rows and the configured analysis results are columns, which is also the layout of the CSV export. `build_results_table` returns a DataFrame indexed by experiment name; the constant `RESULT_NAME_COLUMN` is replaced by `EXPERIMENT_NAME_COLUMN`. The `results_table_instructions` configuration is unchanged.
- HDF5 `SCHEMA_VERSION` bumped to `1.1` for the two new optional `version` attributes (dataset root and per experiment). Older files load unchanged and are stamped on their next save; readers that ignore the attributes are unaffected.
- The time-series component was restructured into documented module-level functions (`build_trace_specifications`, `assign_y_axes`, `build_axis_layout`, `build_figure`, …), so the figure construction is testable without a Streamlit run context. Rendering behavior other than the new units and axes is unchanged.
- `pyKES.utilities.max_rate` reworked to be robust to low-frequency (correlated) sensor noise, which the previous single-length-scale smoother tracked as signal. The trace is now modelled as a slow kinetic component (Matern-5/2) plus a stationary nuisance component (Matern-3/2) plus white noise, and only the kinetic component is differentiated. The nuisance component's correlation time and amplitude are measured beforehand by a robust second-difference variogram rather than fitted by likelihood, because the likelihood alone cannot choose between "the kinetics bent" and "the baseline drifted".
- Artifact handling replaced. Instead of masking samples whose increments look like jumps — which cut out sharp kinetic onsets and, on artifact-rich traces, up to 47 % of the series including the entire initial rise — samples are now rejected only where the data disagree with a prediction from well before *and* a prediction from well after them while those two predictions agree with each other. A genuine transition makes the two sides disagree and is left untouched; a bubble makes them agree and is rejected, then grown over its relaxation tail with hysteresis and undone wherever the trace never returns. Whatever survives is downweighted by redescending (Cauchy) IRLS weights rather than deleted.
- `MaxRateResult` gained a `nuisance` field (the fitted correlated-noise component; `smooth + nuisance` models the measured trace). `smooth` and `rate` now refer to the kinetic component alone, so a plot of `smooth` deliberately does not follow low-frequency wiggles. `hyperparameters` gained `nuisance_lengthscale` and `nuisance_std`; `diagnostics` gained `nuisance_rate_std` and `lengthscale_lower_bound`. `outlier_mask` now marks downweighted rather than deleted samples.
- The uncertainty of `max_rate` is now the mean posterior variance of the derivative across the window. The previous independence bound on the two endpoint values becomes far too conservative once a nuisance component makes the absolute level of the kinetic curve ambiguous.
- New quality flags `max_rate_not_significant` (maximum less than 3 σ above zero, e.g. blank wells), `strong_correlated_noise` (the nuisance component's slope scale reaches the reported rate) and `window_duration_limited` (the series is too short for the sampling-based window rule, so the window holds only a handful of points).
- The default max-rate window is now capped at 10 % of the series duration, on top of the existing floor of 25 median time steps and 2 % of the duration. The floor and the cap cross at exactly 250 samples, so the rule is continuous and series above that length are unaffected.
- **Breaking**: `extract_max_rate` parameters `outlier_threshold` and `outlier_pad` are replaced by a single `robust_threshold` (default 4.0), and `max_fit_points` now defaults to 1200. Reused `hyperparameters` dicts from before this release lack the two nuisance entries and will raise.

### Fixed
- Maximum rates on traces with strong low-frequency noise were overestimated by up to a factor of two, and blank wells reported spurious positive rates driven by noise crests. On a 66-well validation plate the six artifact-rich wells drop by 11–54 %, the six blanks now return near-zero rates flagged `max_rate_not_significant`, and the 60 well-behaved wells reproduce their previous values to within a few percent.
- The Gaussian-process fit could be completely wrong over the first few hundred seconds of a reaction, because the initial rise was masked as an artifact and the smoother reverted to its prior mean across the gap.
- Maximum rates on short, coarsely sampled series were underestimated by up to a quarter, because the sampling-based window floor had no counterpart cap: on a 76-point, 250 s run it produced a window a third of the experiment wide, averaging the maximum together with everything after it. The new duration cap raises such a series from 0.80 to 1.05 µmol/L/s, matching a raw finite-difference reference at the same window to within 1 %.
- On the same short series the noise model collapsed: with only three variogram lags for a four-parameter fit, essentially all of the scatter was assigned to a "correlated" component with a correlation time of 1.5 samples, leaving `white_std` a thousand times too small. That nuisance state then interpolated the measurement noise point by point, driving the residuals — and with them the IRLS scale — to zero, so ordinary noise scored as hundreds of standard deviations and 16 % of the series was rejected as artifacts. A correlated component that decorrelates within three sampling intervals is now folded into the white noise, as are the amplitudes of components already declared insignificant.
- `max_rate_crosscheck` silently became NaN whenever a window held fewer than ten samples, which is the normal case on a short series. The rolling-regression minimum is now scaled to the window.
