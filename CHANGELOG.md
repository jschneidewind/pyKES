# Changelog

All notable changes to this project will be documented in this file.

The format is based on Keep a Changelog, and this project aims to follow Semantic Versioning.

## [Unreleased]

### Added
- **Inherited metadata is now named by the kind of entry that owns it, not by the route that reached it.** `Dopants [finished semiconductor]` is one filter whether the semiconductor was reached through an ordinary catalyst batch or a modified one, where the route-based names put it at two depths and needed folding back together for display. That fold — `merge_key_paths`, `Facet.alternative_keys`, the `COALESCE` branch of `build_expression` — is deleted: the duplicates no longer arise. Two kinds of entry carrying a field of the same name stay two filters, since the kind is part of the name. See [docs/referencing_redesign.md](docs/referencing_redesign.md).
- The change is not a rename. Naming by kind collides — demonstrated on the seeded demo before multi-references existed, where `precursor_chemical_a` and `precursor_chemical_b` both claimed `Supplier [precursor chemical]` — so an inherited field now holds a **set of contributions** and a filter on it is **existential**: it asks whether *some* contributor satisfies it. Two filters over one kind may be satisfied by two different entries, which is usually the question; each filter group carries a **Match one &lt;kind&gt;** checkbox for when it is not, folding them into one lookup anchored on a single contributor.
- **A reference field may name several entries in one cell** — `Precursor Chemicals: EA-1; EA-2; EA-3`, declared `multiple: true` and split on the separators a mapping field already uses. The `edges` primary key becomes `(source, role, target)` with an `ordinal`, and `extract_references` no longer raises on a repeated role: that guard existed because two targets under one role produced identical keys and the second overwrote the first, which sets make impossible. The lettered `Precursor Chemical A`/`B` fields are merged into one, as `Co-catalyst A`/`B` were merged into a mapping.
- `entities.effective` is replaced by two tables. `contributions` holds one row per contributing entry per field — with the value both as text and, where it is one, as a number, and with mapping fields expanded one row per name — and `contribution_sources` holds how each contributor was reached, once per pair rather than repeated on all thirty of its fields. The primary key `(entity_id, contributor, key, sub_key)` **is** the deduplication rule: an entry reached by two routes contributes once, which is what stops a diamond in the graph from counting twice. Both routes are still recorded, for the entry page. Free-text search reads a flattened `search_text` column. Index schema version 2.0, and an index written before it is refused with the repair to run rather than opened — its searches would otherwise return nothing rather than fail.
- The entry page shows each inherited value with the entry that owns it and that entry's kind — *Modified catalyst batch · MOD-001* — and the routes beside it. The property map offers only single-contributor keys as axes: a point whose x averaged three precursor chemicals would sit at a number no experiment has, and nothing on the chart would say so.
- Measured on the finished implementation at 10 000 experiments with three precursors per semiconductor: 114 ms to build every facet against **1130 ms** for the same page under the old design, 40 ms for a dopant range, 69 ms for "any precursor from Merck" and 63 ms for "one precursor both from Merck and pure" — neither of which the old design could express — and 0.1 ms for one entry's provenance, which used to be a graph walk. Ingestion is 2.7 ms per experiment. The index is 118 MB against 21 MB, which is 1.7x what the plan predicted because the real chain contributes about 30 fields per experiment rather than the 19 modelled.
- Two performance findings worth keeping, both from measuring the finished code rather than the design. A first working version cost **2102 ms per page load — worse than what it replaced** — because scoping a facet's bounds with a subquery over `entities` made SQLite drive from the per-entity index and probe once per experiment: 97.8 ms per facet against 1.7 ms for a covering read. That is why `contributions` carries an `entity_type` column it does not logically need. The same mistake in reverse cost the same-entry predicate 237 ms; anchoring it on a row that already satisfies the first condition, rather than on any row of the right kind, brought it to 28 ms.
- [docs/referencing_redesign.md](docs/referencing_redesign.md): a plan, not built, for naming inherited metadata by the **type** of the entry that owns it rather than by the route that reached it — so a modified catalyst batch stops producing a second `Dopants` column, and a field can reference several entries at once. The proposal as stated collides, which was demonstrated on the seeded demo rather than argued: `precursor_chemical_a` and `precursor_chemical_b` are both `precursor_chemical`, so both claim `Supplier [precursor chemical]` today, and multi-references make that the normal case. The plan therefore makes a type-qualified key hold a *set* of contributions, keeping value identity (contributor id + key) separate from column identity (contributor type + key). Measured at 10 000 experiments across three storage shapes: a `contributions` table costs 3.3x the size (69 MB against 21 MB) and wins everything paid repeatedly — 37 ms of facet bounds per page load against 1130 ms today and 608 ms for type-qualified JSON arrays, 9.5 ms per range filter against 43.8 ms, and stored provenance at 0.04 ms rather than a graph walk. Flagged as needing the group's decision: whether a conjunction may be satisfied by different contributors, and whether one type reached at two depths should merge.
- **References that accept more than one kind of entry.** A reference field declares `accepts: [catalyst_batch, modified_catalyst_batch]`, and `modified_catalyst_batch` joins the eight entity types with its own schema and its own example data in the seeded demo. Most of this needed nothing new: an edge carries no target type, and inherited keys are qualified by the *role* rather than by the kind of entry it reached, so `catalyst_batch/Photodeposition wavelength [nm]` means "of whatever this experiment used as its catalyst batch" and one filter spans both kinds. `accepts` is guidance and diagnosis, never a storage constraint — the form's picker offers only accepted kinds, and a wrong-kind link is reported on the admin page rather than refused, because the metadata still merges and discarding it would hide the mistake instead of showing it. The check runs over resolved edges, not at upload: an entry may legitimately name a target that has not arrived yet, and refusing an upload for a fact not yet knowable would break the forward references the ingestion order depends on.
- Omitting `accepts` means the reference is *not checked*, which is deliberately not the same as defaulting it to the role. The plan had proposed that default; it is wrong, because a role names the relationship — `precursor_chemical_a` is filled by a `precursor_chemical` — so the default would have flagged every correct reference in the group's own chain. Every shipped reference field now declares its accepted kinds explicitly.
- **One field reached by several paths becomes one filter.** A modified batch sits between the experiment and the ordinary batch, so the semiconductor is two references away for some experiments and three for the rest, and the registry holds two keys for one field. Two filters would each answer for part of the database and neither would say so — a silently wrong answer, worse than no filter. `merge_key_paths` collects them and `build_expression` reads whichever path an entry has with `COALESCE`, so every operator keeps working unchanged. Merging is by the *last* role and the field name, not the name alone, so a batch's `Notes` and a semiconductor's `Notes` stay apart. Measured on the demo: the dopant filter matches 19 experiments merged against 16 through the shallow path, the three missing ones being exactly those run on a modified batch.
- **Metadata that is a set of named numbers**: a new `mapping` field type for dopants, cocatalysts and synthesis profiles, replacing the lettered `Co-catalyst A`/`B` slots that fixed the count in advance and made "everything with at least 0.02 wt% Cr" depend on which slot somebody filled. A sheet carries one cell of `name=value` pairs — `Ir=0.02; Ru=0.02; Cr=0.03` — with `=` and `:` both accepted, and pairs separated by a semicolon or newline but never a comma, which would be ambiguous wherever Excel writes a decimal comma. A pair that cannot be read is an error, never a silent skip: for a composition that is the difference between "no dopant" and "a dopant we lost". The form renders an editable table with dynamic rows and writes back the same text, so a form entry and an uploaded row produce identical metadata.
- The filter for a mapping is two levels — a picker of the names actually present, then a slider per chosen name over the range that name spans, any number of names at once. Storage needed no change, since `coerce_index_value` already recursed into dictionaries; what did was a `TYPE_MAPPING` in the registry (`infer_value_type` called a dict `text`, which would have offered stringified dictionaries as a multiselect), a `sub_keys` column recording the union of names seen, and a `sub_key` on `Filter` — as its own field rather than a second separator stacked into the key string, which is how the `__SLASH__` bug happened once already.
- **Derived scalars**: a mapping field can declare numbers computed from it at ingestion, because a temperature profile is a sequence and the questions asked of it are aggregates that no per-name slider expresses. `Peak temperature [°C]` (`max_key`) and `Time at peak temperature [h]` (`value_at_max_key`) are stored as ordinary metadata, so each gets a slider, a column and inheritance for free. A mapping whose names are not numbers derives nothing rather than deriving zero, which would be a measurement nobody made.
- `add_missing_columns` adds a column introduced by a newer version to an index that predates it, since `CREATE TABLE IF NOT EXISTS` leaves an existing table exactly as it was. Index schema version 1.1.
- An empty Excel cell arrives as a float NaN rather than as an empty string, so the first pass read it as the text `nan` and reported a filled-in field nobody had filled in. `is_blank` covers None, whitespace and NaN, and every blank check in the schema layer goes through it.
- [docs/database_extensions.md](docs/database_extensions.md): designs for two extensions the group asked for, neither built. **References that accept more than one kind of entry** — an experiment's catalyst batch being either a `catalyst_batch` or a `modified_catalyst_batch`. Most of this already works: an edge carries no target type and inherited keys are qualified by the *role* rather than by the kind of thing it reached, so one filter spans every kind of batch with no union logic. Checked by pointing an experiment's `catalyst_batch` role at a new kind of entry: inheritance continued through it two further hops and an existing two-hop filter matched 61 experiments where it had matched 60. What blocks it is a closed `ENTITY_TYPES` tuple, an `accepts:` field the schema does not have yet, and a form picker with nothing to consult — and the type check belongs at resolution rather than at upload, since refusing an upload for a target that has not arrived yet would break the forward-reference guarantee.
- **Metadata values that are mappings** rather than single numbers — dopants, co-catalysts, temperature profiles — replacing the lettered `Co-catalyst A` / `Co-catalyst B` slots, which fix the count in advance and make "everything with at least 0.02 wt% Cr" depend on which slot somebody filled. Storage needs no change: a mapping round-trips through the `effective` column and arrives intact two references away. The filter the group described — pick a dopant, get a slider for its concentration, repeat — is a JSON path one level deeper than the search already builds: 7.9 ms over 10 000 entities for one dopant's range, 23.2 ms to enumerate the dropdown, and rows lacking the field contribute nothing rather than erroring. The changes needed are a mapping type in the registry (`infer_value_type` calls a dict `text` today, which would offer stringified dictionaries as a multiselect), a sub-key registry, a `sub_key` field on `Filter` rather than a second separator stacked into the key string, and a two-level facet. Sheets declare a mapping as `Ir=0.02; Ru=0.02; Cr=0.03` — typable in Excel without quoting, unlike JSON in a cell. Temperature profiles are noted as the case this does not fit: the questions people ask of them are aggregates, so the recommendation is to keep the mapping for the record and declare derived scalars for the filters.
- Per-entity-type metadata schemas: one hand-editable YAML file in `src/pyKES/database/entity_schemas/` for each of the eight kinds of entry, saying which fields are expected, their types, and the options a choice field allows. They are the group's own vocabulary rather than application code, so they carry comments and are read at runtime. `pyyaml` is a new dependency; the fields for the kinds the example sheets did not cover are marked PLACEHOLDER for the group to replace. New module `pyKES.database.entity_schema`.
- One schema file drives four things, which is the reason to have it: the widgets of the new contribution form, the Excel template offered for download, the validation an upload is checked against, and the reference declarations — a field of type `reference` already says which column links to what, so `GROUP_REFERENCE_INSTRUCTIONS` is now derived from the schemas rather than written a second time that could disagree with them.
- The contribute page gained a **form for adding a single entry**, rendered from the selected type's schema, and a **template download** per entity type generated from the same schema the upload is checked against, so the two cannot drift apart; the template's second sheet says what each column expects. The submitted form is written as a one-row sheet and ingested through the ordinary sheet route rather than writing to the database directly — that is what makes a form entry stored, validated, versioned and rebuildable exactly like an uploaded one.
- Uploads are checked against the schema before anything is written, so a file with one bad row is refused whole rather than leaving half its experiments in the database. A schema states what is *expected*, not what is *allowed*: a declared field filled in wrongly is an error, and a field nobody declared is reported and then accepted, because absorbing metadata that did not exist when the schema was written is what the database is for.
- A rebuild is deliberately not re-validated. Files in the upload store were checked against the schema in force when they arrived and accepted; re-checking them against today's would make every historical upload un-rebuildable the moment a field is made required, destroying the guarantee the upload store exists to provide.
- The browse page is built around comparing a subset, which is the main thing the database is for. Once a search narrows to 50 entries or fewer, the whole matching set — not just the visible page — is plotted by the *existing* `time_series_component`: `build_trace_specifications` and `build_figure` are pure functions over `{name: Experiment}` and an instruction dictionary, so the new panel loads payloads and calls them rather than drawing anything itself. A second multiselect narrows what is drawn without touching the search. The entry page uses the same panel with the entry selection switched off, which deleted the bespoke plotting code it had.
- Payloads now carry the upload's `plotting_instruction`, so a payload describes its own curves and is genuinely a standalone pyKES dataset. Without it a payload loaded as arrays with no way to know which series form a meaningful plot.
- Filters are grouped by the entity they describe and each group is named after it — *Finished semiconductor* rather than *two references away* — with the groups ordered by how far away that entity sits. The entry's own fields are always open and each referenced entity is a collapsed group, so a chain four deep does not bury the fields somebody came to filter on. There is no "more filters" fold: every group is one click from open, because the inherited fields are exactly what a comparison is usually built from. `build_facets` orders by depth *and* by reference path, which is what keeps one entity's fields together.
- **Reset All Filters** clears every filter and the free-text term at once. It runs as a widget callback, because Streamlit refuses to have a widget's state assigned once that widget has been drawn, and it clears the query string with them — the seeding reads the URL, so a reset that left it in place would restore what it had just cleared.
- The query string is now read back as well as written, so a shared search link reproduces the same subset and the same comparison plot. `read_filters_from_url` existed but was never called, which made the documented "a search is a URL" only half true.
- The entry page gained a type-ahead: typing `NB-6` offers every entry starting that way, prefix matches before containments (`search_entity_ids`). Metadata, inherited metadata and results are collapsed expanders, so the page opens on what an entry is and its references rather than on a wall of fields.
- Presentation throughout: stored tokens no longer reach the screen. `display_entity_type` renders `finished_semiconductor` as `Finished semiconductor`, `display_role_path` renders a reference chain as `Catalyst batch › Finished semiconductor`, table headers read `Entity ID` and `Kind` rather than `entity_id` and `entity_type`, and labels are capitalised consistently.
- Styling is Streamlit's own theming in `.streamlit/config.toml` — a dark base with green as the single accent — plus `database_app/styling.py` for the typeface and spacing that configuration cannot express. Two constraints found by running it: the font rule must not select `[class*="st-"]`, because that also matches Streamlit's Material icon spans and renders every expander as the literal text `keyboard_arrow_right`; and the webfont needs a full system fallback, since an instrument network may not reach the font host.
- Phases 3 and 4 of the photocatalysis database: a working Streamlit application over the index, in `pyKES.database_app`, plus `index_query` for the reads it needs. Home, Browse & Search, Entity, Property map, Contribute and Admin, with a `seed_demo` module that builds a synthetic archive four references deep so the whole thing can be opened and tried without any real data. See [docs/database_app.md](docs/database_app.md).
- Search filters are generated from the metadata-key registry scoped to the kind of entry, so a spreadsheet column first seen in next year's uploads gets a working filter with no configuration, and the widget follows from the observed type. Inherited fields appear as ordinary filters captioned with the reference path they came through — in the seeded demo an experiment search offers 23 facets of which 13 are inherited, as deep as `catalyst_batch/finished_semiconductor/precursor_chemical_a`. Filter state and the open entry are written into the query string, so a search and an entry are both links.
- The entity page shows own and inherited metadata separately, the reference graph in both directions (opening a precursor lists every semiconductor made from it), plots the payload's traces, offers it as a standalone HDF5 download, and lets the owner or an admin correct one field at a time — reporting how many descendants the correction moved. The property map plots any two indexed quantities against each other, including ones inherited several references away.
- **Breaking for any index built before this change**: metadata keys are stored with their own slashes escaped. Real keys contain slashes — `Catalyst concentration [g/L]`, `Irradiance A [mW/cm2]`, `Measurement phase [liquid/gas]` — so a reference path joined with `/` could not be split back apart, and facet labels read `L] · via Catalyst concentration [g`. Found by running the application in a browser rather than by testing it. The fix reuses the convention `save_nested_dict_to_hdf5` has always used for the same problem: escape `/` within a key to `__SLASH__`, join components with `/`, and restore each component after splitting. `_sanitize_hdf5_key` is promoted to a public `sanitize_key` / `restore_key` pair with the sentinel as `KEY_SLASH_PLACEHOLDER`, and both the HDF5 layout and the index now use it — one escaping convention in the codebase rather than two, and no key has to be rejected for containing a separator. Existing indexes should be rebuilt from their retained uploads.
- The escaping is enforced in `insert_entity` rather than trusted from callers, and is idempotent, so a key can never be stored raw and later mistaken for a reference path. It is storage detail only: `display_key` restores it everywhere a key reaches the screen, and `stored_metadata_key` converts a hand-written key for a filter — every key that comes from the registry, from `build_facets` or from `list_axis_options` is already in stored form.
- Two further bugs found by running the prototype rather than by testing it. A SQLite connection may only be used by the thread that created it, and Streamlit runs each session's script on a pooled thread, so caching one connection with `st.cache_resource` raised `ProgrammingError` as soon as a second page was opened; `open_shared_index` now keeps a thread-local pool, which WAL mode makes cheap. And the subquery hiding superseded versions aliased a table as `inner`, which is a SQL keyword and a syntax error.
- Metadata keys reach SQLite as bound JSON path parameters rather than as interpolated text, since they arrive from spreadsheet headers; sort columns are checked against a fixed set. 24 tests cover the query layer, including filters one and two references deep, an injection attempt, and facets generated from metadata actually present.
- Phase 1 of the photocatalysis database: four new modules under `pyKES.database` turning uploaded HDF5 batches and metadata sheets into one searchable, cross-referenced SQLite index. `index_schema` holds the tables and the fixed entity vocabulary, `index_registry` the value coercion and the two key registries, `index_references` the reference graph, `index_ingest` the upload path. See [docs/database_index.md](docs/database_index.md); the server it runs on is covered by [docs/server_provisioning.md](docs/server_provisioning.md).
- The table is `entities`, not `experiments`: an experiment is an entity that happens to carry a payload and a precursor chemical one that happens not to, so nothing in these modules knows what a precursor is and a new kind of entry is one string in `ENTITY_TYPES`. Scientific metadata lives in JSON columns, so a metadata column that appears next year needs no migration — it shows up in the entry's JSON, in the key registry, and as a facet.
- Inherited metadata is qualified by the role path that reached it, so `Temperature [°C]` on an experiment and `Temperature [°C]` on its precursor become two distinct keys and the merge is incapable of collision. It is materialised into an `effective` column at ingestion rather than resolved per query, and `find_dependents` recomputes descendants when an ancestor is edited. Forward references (an experiment uploaded before the batch it names) are recorded unresolved and promoted when the target arrives; cycles are capped and reported; a repeated reference role is refused both by `extract_references` and by the `edges` primary key, since two references under one role would produce identical qualified keys and the second would silently overwrite the first.
- Uploads declare their own mapping in `plotting_instruction['index_instructions']` and `['reference_instructions']`, needing no HDF5 schema change. Files predating that fall back to `results_table_instructions`, which already has the required shape, so existing datasets contribute their max rates and quantum yields untouched. Name collisions keep both entries with the newcomer suffixed `__v2`; editing is owner-or-admin via `may_edit`; every upload is stored verbatim under its hash so `rebuild_index` can reconstruct the database from scratch.
- `ExperimentalDataset.save_to_hdf5` gained optional `compression` and `verbose` parameters. Compression is applied only to arrays of at least `COMPRESSION_MINIMUM_ELEMENTS`, because HDF5 refuses to compress scalar datasets outright; the filter is transparent to readers, so a compressed file loads through `load_from_hdf5` unchanged and needs no schema bump. `verbose=False` suppresses the per-experiment print for callers writing one file per experiment in a loop.
- Measured against the group's real 44-experiment plate dataset and their three metadata sheets: ingestion runs at 30 ms per experiment end to end, so a 44-experiment batch completes in 1.3 s and can run synchronously with a progress bar rather than needing a job queue. Payloads come to 136 KB per experiment. Two findings worth recording: gzip takes 6.30 MB only to 5.99 MB here — 1.05x, not the 1.7x measured on an older single-file fixture, because per-file HDF5 overhead across 44 separate payloads offsets most of the saving on high-entropy sensor traces, so budget ~140 KB per experiment; and a leaf metadata name in a reference chain resolves to one path *per entity type* rather than one overall, so `read_metadata_keys` takes an `entity_type` argument and facets must scope by it.
- [docs/photocatalytic_database.md](docs/photocatalytic_database.md): a plan for a private, self-hosted database of the group's photocatalytic results. Users process their own data locally with a pyKES app and upload the resulting HDF5 batch; the server authenticates, splits each upload into per-experiment payloads, and maintains a searchable index. The expensive computation stays on the uploader's machine, so the server only stores bytes, indexes them and answers queries.
- The design problem the plan solves is that the metadata grows: experiments run next year carry fields that do not exist today. The index is therefore a typed core table plus a JSON `metadata` column in SQLite, with two registries (`metadata_keys`, `result_keys`) maintained at ingestion — so a new overview-sheet column needs no migration, and the search page's facets are generated from the registry rather than configured by hand. Key drift (two spellings of one field) and type conflicts are surfaced on an admin page for aliasing rather than silently resolved. Each uploaded file carries its own `index_instructions` inside the existing `plotting_instruction` dictionary, reusing the `results_table_instructions` syntax and requiring no HDF5 schema change.
- A generic reference structure in that plan: entries reference other entries (an experiment names its catalyst batch, which names its precursor, which names its source material) and each entry's effective metadata is its own plus everything inherited transitively, so a search for "synthesised at 1150 C and photodeposited at 360 nm" finds the photocatalytic test two hops away. The `experiments` table generalises to `entities` with an `entity_type`, so an experiment is simply an entity that has a payload and a catalyst batch one that does not — one identity space, one metadata mechanism, one search, and no code that knows what a precursor is. References are declared by the uploaded file in `plotting_instruction['reference_instructions']`, alongside the index mapping, never inferred by scanning values for things that look like IDs.
- Inherited keys are qualified by the role path that reached them (`catalyst_batch/precursor/Synthesis temperature [degC]`), which makes the merge incapable of collision — an experiment and a precursor may both have their own `Temperature [degC]` and they stay distinct — and keeps provenance in the key itself. The key registry gains `leaf_name` and `path` so facets group by leaf and users never have to know the path when only one exists.
- Measured against a synthetic 12 340-entity graph chained four levels deep (10 000 experiments, 2 000 catalyst batches, 300 precursors, 40 source chemicals): resolving every entity's effective metadata takes 165 ms and writing it back 466 ms; the target three-predicate query spanning two inheritance hops runs in 32.9 ms, or 2.7 ms with the two inherited keys promoted to indexed generated columns; finding every dependent of one precursor for invalidation takes 0.2 ms. Materialising beats resolving at query time, where a recursive CTE needs 92.3 ms for a single predicate and requires another join per additional one. The cost is a 3.18x larger index, 7.5 MB to 24.0 MB.
- Two findings on indexing that are easy to discover late. Once one selective index narrows the row set, remaining `json_extract` predicates are free — two promoted keys plus a plain JSON boolean ran in 2.6 ms, the same as the two promoted keys alone — so there is no need to promote everything. And promoting a low-cardinality boolean without running `ANALYZE` made the same query 17.1 ms, because SQLite chose the useless boolean index over the selective range one; `ANALYZE` restored the correct plan and 2.7 ms, so it belongs in the migration rather than in a troubleshooting note.
- Measurements taken for the plan, against a synthetic 10 000-experiment index with an intentionally evolving schema (19 metadata keys for the first 3 000 experiments, 24 for the next 4 000, 30 for the last 3 000): the SQLite index is 16.4 MB including its FTS5 index; a numeric range filter over JSON metadata takes 17.1 ms, three predicates plus a result threshold 4.7 ms, and a property-map query over every active row 14.9 ms. Promoting a hot key to an indexed generated column takes the range filter to 4.3 ms, and FTS5 takes free-text search from 16.5 ms to 1.3 ms. The browser-side alternative at the same scale — the whole index as one wide DataFrame — costs 2.05 MB gzipped, 15.9 MB resident and 66.5 MB peak allocation per page load, which is what decided the index against being loaded client-side.
- One finding worth recording because it is easy to hit: SQLite's `ALTER TABLE` accepts only `VIRTUAL` generated columns, not `STORED` (`cannot add a STORED column`). `VIRTUAL` columns can still be indexed and the index carries the speed-up, so hot-key promotion works — but the migration must say `VIRTUAL`.
- Ingestion measurements on `src/tests/data/260507_Complete.h5`: splitting an uploaded multi-experiment file into per-experiment payloads costs 14.8 ms per experiment with gzip compression (13.8 ms without, so compression is essentially free in time and saves 33% of disk). A 40-experiment upload therefore splits in about 0.6 s and a full 10 000-experiment rebuild in about 2.5 minutes, which means ingestion can run synchronously with a progress bar — no job queue, worker process or broker.
- Earlier measurements retained from the first version of the plan, on the same fixture: 96.3 KB of array bytes per experiment against ~0.2 KB of metadata, and gzip level 4 giving 1.7x on the file as a whole (2.2x with float32 display copies).

### Fixed

- Chosen table columns appeared to do nothing on the browse page. They were in the table all along — the CSV export proved it — but each header carried its whole reference chain (`Synthesis temperature [°C]  ·  via Catalyst batch › Finished semiconductor`), so three or four of them were wider than the viewport and every further column landed off-screen behind the fixed kind, group and owner columns. The chain moved to the header's tooltip, the header is the field name alone, and the chosen columns now sit directly after the identifier. Two chosen columns sharing a field name are told apart by the entity they came from, which also closes a silent overwrite: they previously collided into one dictionary key, so one of them really did disappear.
- The reference links on the entry page did nothing. The type-ahead's text box was keyed globally and kept whatever had last been searched for, so every click navigated to the new entry and was then sent straight back by the stale term. Its widgets are now keyed by the entry currently open, which retires the old box on navigation; assigning to a widget's state directly is not available, since Streamlit refuses it once the widget has been drawn.
- The search box showed the previous term instead of what had just been typed, on every other search. Streamlit derives an unkeyed widget's identity from its arguments, so seeding the box with `value=` from the query string made it a *different* widget as soon as the search reached the URL, and it came back holding the older value. The box and the kind selector now carry keys and are seeded from the URL once.
- `pyarrow.ArrowTypeError` on the console whenever an entry was opened. One column holding every field's value necessarily mixes numbers, text and booleans, which Arrow cannot serialise; Streamlit logged a traceback and then silently repaired the table. `arrow_safe_frame` renders only the columns pandas could not type, so a column of numbers keeps its alignment, its sort and Streamlit's formatting rather than being printed at full float precision.

## [0.2.1]

### Fixed
- The ingestion progress bar on the Data Upload page never appeared in the browser deployment: pressing "🚀 Process data" showed nothing at all until processing had finished. stlite runs Streamlit inside Pyodide on the browser's single event loop, with no separate script-runner thread, so everything `read_in_experiments_single_threaded` wrote through its `progress_callback` was queued and only delivered once the loop it was reporting on had ended — at which point the page cleared the placeholder and drew the result messages instead. Under `streamlit run` the same code worked, because there the script has a thread of its own while the server's event loop keeps delivering. The reprocessing section had the same defect.
- Ingestion and reprocessing are now spread across Streamlit runs, one experiment each, by the new module `pyKES.streamlit_app.chunked_processing`. A run has to end for what it drew to reach the browser, so the job is stepped by two `st.fragment`s with a `run_every` timer: `render_job_progress` draws the bar and nothing else, `advance_job` processes one experiment and draws nothing. `any_active_job` lets a page skip sections too expensive to re-render per experiment (the Data Upload page skips the HDF5 merge, the download button, the overview table and the statistics until the job is done), and uploaded files are staged in a `mkdtemp` directory that outlives the run which created them, removed when the job finishes. See [docs/browser_deployment.md](docs/browser_deployment.md).
- Both halves of that design are forced by how Streamlit delivers messages, and both were established by measuring the deployed page in headless Chrome. Stepping the job with `st.rerun()` shows **nothing at all** in the browser: `AppSession` clears unflushed messages on every `SCRIPT_STARTED`, and a run that ends in `st.rerun` is followed immediately by the next one, so the bar is discarded before it is sent. (On a server it survives, because the flush runs on another thread — which is why this looked fixed under `streamlit run`.) Drawing the bar inside the working fragment fails too, less obviously: `ForwardMsgQueue.clear` preserves the deltas of fragments *other* than those rerunning, so a fragment wipes its own output on its own next tick — the browser showed `Processing experiment 1/8` for a whole eight-experiment run and never advanced.
- Expect a bar that appears immediately and climbs, but not once per experiment: the single browser worker thread is busy processing, so only some paints reach the page (three or four distinct states over eight experiments in a probe). Changing the timer interval does not change that.
- A dataset created in a browser (stlite) deployment recorded `'version': None` as the external app's provenance. `get_project_version` reads the app's `pyproject.toml` from disk, but a stlite bundle holds only the files its build script writes into Pyodide's filesystem — `.py` modules and nothing else — so the upward search reached the filesystem root and found none. There is no repository in the browser either, which is why the commit-based stamp it replaces failed there in the same way. The build script has to bundle `pyproject.toml` beside the app package (pyKES-Well-App's `deploy/build.py` now does), and [docs/browser_deployment.md](docs/browser_deployment.md) gained a section on what the bundle must carry besides the modules, with a check that reads the version back out of the built layout.

### Changed
- `pyKES.database.data_processing` exposes the per-experiment steps of both loops as module-level functions: `ensure_processed_column`, `select_unprocessed_experiments`, `ingest_experiment`, `select_experiments_to_reprocess`, `reprocess_experiment_by_name` and `finalize_processing_run`. The seeding of the `Processed` flag as the string `'False'` — the 0.2.0 fix for `TypeError: Invalid value 'True' for dtype 'bool'` — now lives in `ensure_processed_column`, which both `select_unprocessed_experiments` and `ingest_experiment` call, so stepping through experiments one rerun at a time reaches the flag with the same guarantee the loop function had. `read_in_experiments_single_threaded`, `read_in_experiments_multiprocessing` and `reprocess_experiments` are now thin loops over them and keep their signatures, return values and `progress_callback` protocol unchanged, so callers outside Streamlit are unaffected.
- The three submit buttons on the Data Upload page pass `width="stretch"` instead of the deprecated `use_container_width`.
- Removed `_update_ingestion_progress` from the data-upload component; the progress bar is drawn by `chunked_processing.paint_job_progress` and needs no `st.empty` placeholder.
- **Breaking**: the external app's provenance is now its own released version rather than its git commit. `pyKES.utilities.version_information.get_git_commit` is replaced by `get_project_version`, which searches upwards from a given path for the nearest `pyproject.toml` and returns the version declared in it — every external repo embedding pyKES is a Python project with one, and the version number is the identifier its users, issues and changelog refer to, whereas a commit hash only means something to whoever has the repository at hand. The recommended entry becomes `{'app': 'photocat', 'version': get_project_version(__file__)}`; `external_version` stays free-form, so existing dictionaries (including `'commit'` entries in already-written HDF5 files) keep working untouched. `read_version_from_pyproject` now takes the file to read, and the module-level `PYPROJECT_PATH` is renamed `PYKES_PYPROJECT_PATH`. Since the stamp is now a release number, bump the app's version when its processing behaviour changes. See [docs/versioning_and_reprocessing.md](docs/versioning_and_reprocessing.md).

## [0.2.0]

### Added
- Real-data tests for `max_rate`: `src/tests/test_max_rate_real_data.py` runs the pipeline over eleven measured traces committed as plain two-column CSVs in `src/tests/data/max_rate_real/` — five PyroScience oxygen logs, two UniAmp hydrogen logger exports, two short hand-logged runs and the two well-plate wells either side of the nuisance resolution floor (`AE-855_B2`, `AE-855_C2`). They check what synthetic ground truth cannot: that kinetic plus nuisance reproduce each measured trace to within its fitted noise, that the smoothing-free cross-check never disagrees enough to be flagged, and that each of the three branches of the noise characterization is reached by the real data that belongs in it. Reference maximum rates are pinned at 5 % so a change in behaviour on real files has to be looked at rather than absorbed. See the README beside the fixtures for their provenance.

### Fixed
- `pyKES.utilities.max_rate` could report a rate driven by correlated sensor noise when that noise decorrelated close to three sampling intervals. The resolution guard added in 0.1.7 discarded a correlated component whose measured correlation time fell below that floor and re-labelled its whole amplitude as white noise, which left the kinetic Matérn-5/2 as the only component able to explain wiggles that are in fact correlated — so its length scale collapsed onto them and a noise crest became the reported maximum. The guard was all-or-nothing, so a fit landing a fraction of a percent below the floor was treated completely differently from one landing just above it. On a 110-well plate, one well (AE-855_B2) missed the floor by 0.4 % with correlated noise 65 times the white variance and came out 17 % high (0.0438 instead of 0.0364 µmol/h) on a rate curve that oscillated between −0.03 and +0.07 µmol/h instead of decaying — and raised no flag, because the fold also set the nuisance correlation time to the one value that suppresses `strong_correlated_noise`.
- The floor is now a constraint rather than a verdict: a correlation time below `NUISANCE_MIN_LENGTHSCALE_STEPS` sampling intervals is pinned there and the white and correlated variances are refitted under that constraint, so the component is kept instead of deleted. The refit matters — a process held to a longer correlation time explains less of the short-lag variogram and has to return the difference to the white noise, which is what keeps the clamp from understating `white_std` (by a factor of 2.9 on a simulated nuisance at 1.2 sampling intervals). Folding to white now happens only for the two cases that genuinely leave nothing to measure: a component carrying less than `CORRELATED_NOISE_SIGNIFICANCE` of the white variance, and a variogram with fewer lags than the new `VARIOGRAM_MIN_RESOLVED_LAGS` (6), the four-parameter model having no headroom below that. The latter is the real cause of the short-series collapse fixed in 0.1.7, which the old lengthscale test only caught as a symptom; that regression stays covered. New module-level helper `variogram_residuals_at_fixed_lengthscale` performs the constrained refit.
- Rerunning all 110 wells of the plate, AE-855_B2 is the only result that moves; the other 109 are bit-identical, since neither new branch is reached when the variogram resolves a correlation time above the floor.
- `read_in_experiments_single_threaded` raised `TypeError: Invalid value 'True' for dtype 'bool'` as soon as the first experiment succeeded, whenever `overview_df` arrived without a `Processed` column — the ordinary first-ingestion case. The column holds the strings `'True'` / `'False'` everywhere else (it round-trips through Excel and HDF5, and is read back with `dtype=str`), but it was seeded with a bool `False`, giving it bool dtype; current pandas refuses to write a string into that instead of silently upcasting to object as it used to. The same mismatch also made the skip-already-processed mask ineffective, since `.ne('True')` against a bool column is true for every row, so a second ingestion pass would have reprocessed everything.
- Running `pytest` from the repository root hung before a single test started. Collection reached `Untracked/`, whose `plotting_links_test.py` matches pytest's `*_test.py` pattern and draws a figure at import; `plt.show()` then blocked on the window forever. New `[tool.pytest.ini_options]` in `pyproject.toml` points `testpaths` at `src/tests` and adds `Untracked` to `norecursedirs`, so both `pytest` and `pytest .` collect in under a second.

## [0.1.7]

### Added
- Dataset version information: `ExperimentalDataset.version` is a new top-level dictionary (alongside `plotting_instruction`, `group_mapping` and `processing_parameters`) recording the pyKES version, the schema version, the creation, last-modification and last-processing timestamps, and a free-form `external_version` entry for the embedding app. It is written into the HDF5 root as a JSON attribute and shown on the Home and Data Upload pages. Each `Experiment` carries the same kind of dictionary in `Experiment.version`, stamped whenever that experiment is processed, so partial reprocessing runs stay traceable. New module `pyKES.utilities.version_information` provides the helpers, including `get_git_commit` for external apps that want to record the commit of their own processing code; `ExperimentalDataset.set_external_version` and the new `DataUploadConfig.external_version` field feed it in. See [docs/versioning_and_reprocessing.md](docs/versioning_and_reprocessing.md).
- Reprocessing of existing HDF5 files: `pyKES.database.data_processing.reprocess_experiments` (and `reprocess_single_experiment`) rerun the processing step against the metadata and raw data already stored in a dataset, rebuilding `processed_data` without the original raw-data files — the path for applying an improved algorithm to finished files. The metadata is either reused as stored or refreshed from `overview_df` via the optional `metadata_retrival_function`, which also updates `color` and `group`. Experiments whose processing raises keep their previous results. Exposed on the Streamlit Data Upload page as "3. ♻️ Reprocess Existing Experiments", with pipeline and experiment selection, a metadata-refresh toggle and a progress bar.
- Units on the Time-Series page: `time_series_instructions` entries accept optional `'unit_x'` / `'unit_y'` keys, each either a path into the experiment holding the unit string or a literal unit. Units become the axis titles and appear in the hover box. Curves whose y unit differs are drawn against their own y axis, added on the right-hand side, so amounts (`umol`) and rates (`umol / s`) can be shown in one figure. Instructions without units keep the previous single-axis behavior with generic axis titles. See [docs/plotting_instructions.md](docs/plotting_instructions.md).
- Progress reporting for raw-data ingestion: `read_in_experiments_single_threaded` accepts an optional `progress_callback`, called as `(completed, total, experiment_name)` once before the loop (with `total` and `None`) and after each experiment. The Streamlit data-upload page uses it to render a live progress bar naming the experiment being processed.

### Changed
- `streamlit` is now required at `>=1.49`. The components pass `width="stretch"` to `st.dataframe` / `st.plotly_chart`, which older versions reject with `proto.width = width` raising a type error when a page renders a table or a figure.
- **Breaking (display only)**: the analysis results table is transposed — experiments are now rows and the configured analysis results are columns, which is also the layout of the CSV export. `build_results_table` returns a DataFrame indexed by experiment name; the constant `RESULT_NAME_COLUMN` is replaced by `EXPERIMENT_NAME_COLUMN`. The `results_table_instructions` configuration is unchanged.
- HDF5 `SCHEMA_VERSION` bumped to `1.1` for the two new optional `version` attributes (dataset root and per experiment). Older files load unchanged and are stamped on their next save; readers that ignore the attributes are unaffected.
- The time-series component was restructured into documented module-level functions (`build_trace_specifications`, `assign_y_axes`, `build_axis_layout`, `build_figure`, …), so the figure construction is testable without a Streamlit run context. Rendering behavior other than the new units and axes is unchanged.
- `pyKES.utilities.max_rate` reworked to be robust to low-frequency (correlated) sensor noise, which the previous single-length-scale smoother tracked as signal. The trace is now modelled as a slow kinetic component (Matern-5/2) plus a stationary nuisance component (Matern-3/2) plus white noise, and only the kinetic component is differentiated. The nuisance component's correlation time and amplitude are measured beforehand by a robust second-difference variogram rather than fitted by likelihood, because the likelihood alone cannot choose between "the kinetics bent" and "the baseline drifted".
- Artifact handling replaced. Instead of masking samples whose increments look like jumps — which cut out sharp kinetic onsets and, on artifact-rich traces, up to 47 % of the series including the entire initial rise — samples are now rejected only where the data disagree with a prediction from well before *and* a prediction from well after them while those two predictions agree with each other. A genuine transition makes the two sides disagree and is left untouched; a bubble makes them agree and is rejected, then grown over its relaxation tail with hysteresis and undone wherever the trace never returns. Whatever survives is downweighted by redescending (Cauchy) IRLS weights rather than deleted.
- `MaxRateResult` gained a `nuisance` field (the fitted correlated-noise component; `smooth + nuisance` models the measured trace). `smooth` and `rate` now refer to the kinetic component alone, so a plot of `smooth` deliberately does not follow low-frequency wiggles. `hyperparameters` gained `nuisance_lengthscale` and `nuisance_std`; `diagnostics` gained `nuisance_rate_std` and `lengthscale_lower_bound`. `outlier_mask` now marks downweighted rather than deleted samples.
- The uncertainty of `max_rate` is now the mean posterior variance of the derivative across the window. The previous independence bound on the two endpoint values becomes far too conservative once a nuisance component makes the absolute level of the kinetic curve ambiguous.
- New quality flags `max_rate_not_significant` (maximum less than 3 σ above zero, e.g. blank wells), `strong_correlated_noise` (the nuisance component's slope scale reaches the reported rate) and `window_duration_limited` (the series is too short for the sampling-based window rule, so the window holds only a handful of points).
- The default max-rate window is now capped at 10 % of the series duration, on top of the existing floor of 25 median time steps and 2 % of the duration. The floor and the cap cross at exactly 250 samples, so the rule is continuous and series above that length are unaffected.
- **Breaking**: `extract_max_rate` parameters `outlier_threshold` and `outlier_pad` are replaced by a single `robust_threshold` (default 4.0), and `max_fit_points` now defaults to 1200. Reused `hyperparameters` dicts from before this release lack the two nuisance entries and will raise.

### Fixed
- Maximum rates on traces with strong low-frequency noise were overestimated by up to a factor of two, and blank wells reported spurious positive rates driven by noise crests. On a 66-well validation plate the six artifact-rich wells drop by 11–54 %, the six blanks now return near-zero rates flagged `max_rate_not_significant`, and the 60 well-behaved wells reproduce their previous values to within a few percent.
- The Gaussian-process fit could be completely wrong over the first few hundred seconds of a reaction, because the initial rise was masked as an artifact and the smoother reverted to its prior mean across the gap.
- Maximum rates on short, coarsely sampled series were underestimated by up to a quarter, because the sampling-based window floor had no counterpart cap: on a 76-point, 250 s run it produced a window a third of the experiment wide, averaging the maximum together with everything after it. The new duration cap raises such a series from 0.80 to 1.05 µmol/L/s, matching a raw finite-difference reference at the same window to within 1 %.
- On the same short series the noise model collapsed: with only three variogram lags for a four-parameter fit, essentially all of the scatter was assigned to a "correlated" component with a correlation time of 1.5 samples, leaving `white_std` a thousand times too small. That nuisance state then interpolated the measurement noise point by point, driving the residuals — and with them the IRLS scale — to zero, so ordinary noise scored as hundreds of standard deviations and 16 % of the series was rejected as artifacts. A correlated component that decorrelates within three sampling intervals is now folded into the white noise, as are the amplitudes of components already declared insignificant.
- `max_rate_crosscheck` silently became NaN whenever a window held fewer than ten samples, which is the normal case on a short series. The rolling-regression minimum is now scaled to the window.
